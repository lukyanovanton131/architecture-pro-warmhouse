# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах.
- Система поддерживает получение данных о температуре с датчиков, установленных в домах. 
- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.
- Система поддерживает получение данных о температуре с датчиков, установленных в домах.
- Самостоятельно подключить свой датчик к системе пользователь не может.

### 2. Анализ архитектуры монолитного приложения

- **Язык программирования:** Go
- **База данных:** PostgreSQL
- **Архитектура:** Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
- **Взаимодействие:** Синхронное, запросы обрабатываются последовательно.
- **Масштабируемость:** Ограничена, так как монолит сложно масштабировать по частям. Вертикальное масштабирование.
- **Развертывание:** Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

В текущем приложении можно выделить следующие домены:
 - домен "Управление устройствами отопления" (включает в себя кейсы по включению/отключению приборов отопления через реле)
 - домен "Мониторинг температуры" (включает кейсы по сбору показателей с датчиков температуры)
 - домен "Администрирование" (включает кейсы по регистрации новых датчиков температуры и реле управления устройствами отопления и новых клиентов)

В новой архитектуре приложения для реализации бизнес требований нужно выделить следующие домены:
 - домен "Управление устройствами"
 - домен "Сбор телеметрии"
 - домен "Администрирование"

### **4. Проблемы монолитного решения**

- трудно/невозможно добавить новые виды устройств, новые протоколы управления устройствами, так как это повышает общую сложность системы, а повышение сложности увеличивает % возникновения ошибок. По опыту, часто при добавлении нового ломается старое, где даже не было изменений в коде. 
- если произойдет ошибка в коде по управлению устройствами, то упадет и сбор телеметрии.
- если возрастет нагрузка от сбора данных телеметрии в результате подключения новых устройств из новых подключенных поселков, необходимо будет либо вертикально масштабировать путем выделения добполнительных CPU, памяти и т.д, что без остановки приложения невозможно, либо горизонтально масштабировать запуская новые инстансы всего монолитного приложения. Оба варианта приведут к неоптимальному расходованию вычислительных мощностей.
- при расширении штата команды разработки повышается сложность управления и координации.
- увеличивается время доставки в прод новых фич, так как требется тестирование почти весь монолит, а иногда и полный регрес.

# Задание 4. Создание и документирование API


### 1. Тип API

Укажите, какой тип API вы будете использовать для взаимодействия микросервисов. Объясните своё решение.
Для взаимодействия микросервисов используетя:
 - синхронное API с использованием архитектурного стиля REST 
 - асинхронное API через брокер сообщений Kafka

Синхронный вариант используется там где необходимо сразу узнать о результате выполнения запроса. 
Например, пользователь шлет запрос на включение устройства. В этом случае более дружественный вариант взаимодействия 
с ним будет сразу сообщить об успехе или о проблемах. Если сервис получит команду на включение устройства в будущем,
то это может быть даже опасно, например открытие ворот.

Асинхронный вариант лучше подойдет для сбора данных телеметрии, тут их можно обрабатывать потоком, например Kafka Stream.
